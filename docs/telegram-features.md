# امکانات تلگرام: فهرست جامع و مشخصات قابل پیاده‌سازی

> **دامنه:** کلاینت موبایل و دسکتاپ تلگرام (رفتار محصولی)، مهندسی معکوس به مشخصات فنی برای پیام‌رسان وب فارسی **HssNGram** (React 19 + Vite + Zustand / Node 24 + Express 5 + Socket.IO / PostgreSQL / S3).
> **تاریخ بررسی:** ۸ نوامبر ۲۰۲۶ — مستندات API تلگرام در زمان بررسی، **Layer 223** را اعلام می‌کند.
> **روش:** فقط منابع رسمی تلگرام (`telegram.org/faq`، `telegram.org/blog`، `core.telegram.org/*`) خوانده شده است. هیچ کد پروژه تغییر نکرده؛ این سند فقط پیشنهاد است.

---

## ۰. راهنمای خواندن سند

### سه سطح شاهد

| سطح | معنی | نشانه در متن |
| --- | --- | --- |
| **مستند رسمی** | عیناً از صفحه رسمی تلگرام خوانده شده | لینک در همان ردیف |
| **استنباط مهندسی** | نتیجه‌گیری من درباره وب/پشته این پروژه، نه ادعای تلگرام | برچسب «استنباط» |
| **بررسی‌نشده** | فقط عنوان/وجود صفحه دیده شده، جزئیات خوانده نشده | بخش ۸ |

### معنی ستون‌ها

- **پیچیدگی در وب:** `کم` = چند ساعت تا یک روز · `متوسط` = دو تا پنج روز · `زیاد` = بیش از یک هفته یا نیاز به سرویس جانبی.
- **نیاز به تغییر بک‌اند:** `خیر` = فقط فرانت · `جزئی` = بدون مهاجرت دیتابیس (فیلد `meta` یا تنظیمات) · `بله` = مهاجرت + منطق سرور.
- **اولویت:** `P0` اکنون · `P1` نسخه بعد · `P2` بعدتر · `P3` اختیاری یا شاید هرگز.

> نکته مهم: تلگرام یک پروتکل است، نه یک UI. رفتارهایی که اینجا «رفتار تلگرام» نامیده می‌شود، از مستندات API و FAQ استخراج شده و ممکن است در کلاینت موبایل و دسکتاپ از نظر چیدمان منو تفاوت داشته باشد.

## ۱. جمع‌بندی در یک نگاه

- تلگرام سه ستون دارد که بقیه امکانات روی آن سوار است: **مدل Peer** (کاربر/گروه/کانال)، **ترتیب سراسری پیام (`seq`/`pts`)** و **صف سمت سرور** برای هر چیزی که «بعداً» اتفاق می‌افتد (زمان‌بندی، پردازش ویدیو، TTL).
- بیشتر قابلیت‌هایی که کاربر «ساده» می‌بیند، در واقع **وضعیت سمت سرور** هستند: پیش‌نویس همگام بین دستگاه‌ها، صف زمان‌بندی مستقل برای هر چت، شمارنده واکنش با ترتیب انتخاب ([مستند زمان‌بندی](https://core.telegram.org/api/scheduled-messages)، [مستند پیش‌نویس](https://core.telegram.org/api/drafts)، [مستند واکنش‌ها](https://core.telegram.org/api/reactions)).
- بزرگ‌ترین شکاف‌های HssNGram امروز **کانال (broadcast)**، **تاپیک**، **مجوزهای ریز ادمین** و **حریم خصوصی قابل تنظیم** است؛ چون مدل داده فعلی `chats.type` را به `direct` و `group` محدود کرده و نقش‌ها فقط سه مقدار `owner/admin/member` دارند.
- ارزان‌ترین بردها با بیشترین اثر روزمره: **سنجاق چندتایی، فوروارد با مبدأ، نقل‌قول بخشی از متن، ارسال بی‌صدا**.
- گران‌ترین‌ها: **تماس گروهی در مقیاس بالا**، **استیکر متحرک**، **همگام‌سازی چنددستگاهی کامل** و **تضمین خودتخریبی**.

## ۳. پانزده قابلیت کلیدی: مشخصات فنی

> مسیرها و نام رویدادها با قواعد موجود پروژه نوشته شده‌اند (`/api/...`، رویدادهای دونقطه‌ای مثل `message:new`، `chat:update`، `call:state`). هرجا نام رویداد فعلی متفاوت است، فقط نگاشت کنید؛ کد فعلی تغییر نمی‌کند.

### ۳.۱ ویرایش پیام

| مؤلفه | مشخصات پیشنهادی |
| --- | --- |
| جدول/ستون | `messages.edited_at` (موجود) + `messages.edit_count int default 0` + `messages.meta->>'lastEditBy'` برای ثبت ویرایش ادمین |
| رویداد سوکت | `message:update` (موجود) با `{ id, body, editedAt, editCount }`؛ برای اعضای چت `chat:update` هم بفرست تا پیش‌نمایش فهرست تازه شود |
| مسیر API | `PATCH /api/messages/:id` (موجود) — بدنه `{ body }`؛ فقط فرستنده یا ادمین با مجوز `edit_messages` |
| نکته UX | برچسب «ویرایش‌شده» کنار زمان؛ در RTL برچسب باید در سمت چپ زمان بنشیند؛ ویرایش باید بدون بستن کادر پیام و با `Escape` لغو شود. تلگرام اجازه می‌دهد ویرایش برای دیگران نمایان نباشد ([ساختار Message](https://core.telegram.org/constructor/message)) — در نسخه ما شفافیت را پیشنهاد می‌کنم |

### ۳.۲ حذف برای من / برای همه

| مؤلفه | مشخصات پیشنهادی |

| جدول/ستون | `messages.deleted_at` برای «برای همه» + جدول جدید `message_deletions(message_id, user_id, deleted_at, primary key(message_id, user_id))` برای «برای من» |

## ۶. ترتیب پیشنهادی اجرا

**فاز ۱ — پایه‌های اعتماد و کنترل (بدون تغییر مدل داده بزرگ)**
حذف برای من/همه + پاک‌کردن تاریخچه، سنجاق چندتایی، ارسال بی‌صدا، فوروارد با مبدأ، نقل‌قول بخشی.

**فاز ۲ — زمان و وضعیت**
زمان‌بندی ارسال، پیش‌نویس همگام، حریم خصوصی آخرین بازدید و تیک، بلاک، ورود دو مرحله‌ای.

**فاز ۳ — ساختار گروه**
مجوزهای ریز ادمین، سکوت/بن با مدت، لینک دعوت با انقضا و سقف، درخواست عضویت، جستجوی فیلترشده.

**فاز ۴ — قالب‌های محتوایی**
نظرسنجی، آلبوم، تاپیک، کانال، پوشه‌بندی، TTL.

**فاز ۵ — سنگین‌ها**
تماس گروهی با SFU، استیکر متحرک، ربات و مینی‌اپ، محافظت از محتوا.

### پنج قابلیتی که اول باید اضافه شوند

1. **حذف برای من + پاک‌کردن تاریخچه** — کم‌هزینه، اثر مستقیم بر حریم خصوصی، و پیش‌نیاز ذهنی کاربران برای اعتماد.
2. **مجوزهای ریز ادمین (به‌همراه سکوت/بن مدت‌دار)** — بدون آن، هر گروه بزرگ به آشوب می‌رسد.
3. **لینک دعوت با انقضا/سقف + درخواست عضویت** — ورود کنترل‌شده، جایگزین امن «همه می‌توانند عضو شوند».
4. **بسته ارسال: زمان‌بندی + بی‌صدا** — دو قابلیت پرتقاضا با یک تغییر کوچک در مدل پیام.
5. **سنجاق چندتایی + فوروارد با مبدأ + نقل‌قول** — بیشترین بهبود روزمره به ازای کمترین کار.

> گزینه ششم که تقریباً هم‌رده است: **حریم خصوصی آخرین بازدید/تیک خواندن**؛ اگر کاربران خانواده‌ای هستند و حساسیت دارند، آن را به فاز ۱ منتقل کنید.

## ۸. آنچه بررسی نشد

- **پست‌های تکی بلاگ** فقط از فهرست عنوان‌ها دیده شد؛ برای نمونه «Rich Text Editor, Communities, Ephemeral Messages in Groups» (۱۴ جولای ۲۰۲۶) اعلام شده اما جزئیات رفتارش خوانده نشده و در جدول‌ها ادعایی درباره‌اش نیست.
- **جزئیات UI موبایل و دسکتاپ** (چیدمان منوها، تفاوت‌های نسخه iOS/Android) بررسی نشده؛ این سند رفتار پروتکل و محصول را توصیف می‌کند، نه پیکسل‌ها.
- **قابلیت‌های Premium** فقط جایی که در مستندات صریح بود (مثل تکرار زمان‌بندی) ذکر شد؛ فهرست کامل Premium بررسی نشد.
- **صفحه takeout** (برون‌بری داده) و **passkeys** فقط وجودشان در فهرست API/بلاگ دیده شد، نه جزئیات.
- **محدودیت‌های نرخ** (`FLOOD_WAIT`) و سقف‌های عددی دقیق (تعداد پین، سقف واکنش) به مقادیر پیکربندی سرور تلگرام وابسته‌اند و در این سند عدد قطعی داده نشده.
- **ربات‌ها و مینی‌اپ‌ها** در سطح مفهوم (FAQ) بررسی شد، نه Bot API؛ اگر لازم شد، مستند جدا می‌خواهد.
