## ۱. خلاصهٔ محصول

HssNGram یک پیام‌رسان خصوصی برای خانواده و دوستان است، شبیه تلگرام، با رابط فارسی RTL و قابلیت نصب به‌عنوان PWA. هدف استقرار: ابر آروان روی دامنهٔ `hssngram.hssn.my.id`.

- **معماری:** تک‌سرویس. React 19 + Vite در مرورگر؛ Node.js 24 / Express 5 / Socket.IO در سرور؛ PostgreSQL 16 برای داده؛ S3 آروان یا دیسک برای فایل؛ `coturn` برای TURN.
- **احراز هویت:** شناسهٔ ۸ رقمی + گذرواژه (`scrypt`)، توکن دسترسی ۲۰ دقیقه‌ای، refresh چرخشی ۶۰ روزه، تأیید ادمین برای حساب جدید.
- **مدل داده:** `users`، `chats`، `chat_members`، `messages`، `attachments`، `message_reactions`، `message_hidden`، `calls`، `call_participants`، `poll_votes`، `user_blocks`، `chat_invites`، `push_subscriptions`، `guests`، `support_threads`، `support_messages`.
- **کد:** `apps/server` (سرویس‌ها/روت‌ها/ریل‌تایم/استوریج) و `apps/web` (کامپوننت‌ها/صفحه‌ها/استور Zustand).

## ۳. اجرا، تست و دیپلوی

### ۳.۱ پیش‌نیازها

- Node.js **≥ 22** (طبق `engines`؛ CI از Node 24 استفاده می‌کند)
- npm 10+
- برای اجرای محلی **نیازی به نصب پستگرس نیست** — `db:dev` یک PGlite روی پورت `55432` بالا می‌آورد
- برای دیپلوی: سرور Ubuntu 24.04 با Docker و docker compose plugin

### ۳.۲ اجرای محلی

```bash
npm install

npm run db:dev        # PGlite روی 127.0.0.1:55432 (ترمینال جداگانه)
cp apps/server/.env.example apps/server/.env
# داخل .env حداقل این‌ها را ست کنید: DATABASE_URL, JWT_SECRET, PUBLIC_URL

npm run migrate       # اعمال مایگریشن‌ها
npm run seed          # ساخت ادمین 10000000 / 427726
npm run dev           # API روی :8080 و Vite روی :5173
```

- رابط کاربری: <http://localhost:5173>
- صفحهٔ پشتیبانی عمومی: `/support`
- سلامت سرویس: `GET /api/health`
- نسخهٔ تولیدی محلی: `npm run build` سپس `npm start` روی <http://localhost:8080>

**نکته:** `db:dev` باید در یک ترمینال جداگانه باز بماند؛ بستن آن یعنی قطع اتصال دیتابیس.

### ۳.۳ تست و کیفیت

```bash
npm test              # build سرور + ۳۳ تست یکپارچه روی PGlite
npm run typecheck     # بررسی نوع در server و web
npm run build         # ساخت وب (Vite) و کامپایل سرور (tsc)
```

- تست‌ها روی **PGlite در حافظه** اجرا می‌شوند؛ به پستگرس بیرونی، داکر یا شبکه وابسته نیستند.
- پوشش فعلی: ثبت‌نام/تأیید ادمین، ورود، چرخش نشست، چت خصوصی و گروه، ترتیب و شمارش پیام، کنترل دسترسی، ویرایش/حذف/واکنش، آپلود و لینک امضاشده، چرخهٔ سیگنالینگ تماس، جستجوی فارسی، غیرفعال‌سازی کاربر، افزودن/حذف کاربر توسط ادمین، گفتگوی مهمان و تبدیل به کاربر، فوروارد/سنجاق/حذف برای من، جستجوی درون‌چت، آلبوم/بی‌صدا/نظرسنجی، زمان‌بندی، TTL، حریم خصوصی/بلاک/خروجی داده، Saved Messages، کانال و لینک دعوت، slow mode و حقوق اعضا، فوروارد ناشناس.
- **آنچه پوشش داده نمی‌شود:** رفتار مرورگر (UI)، تماس واقعی با مدیا، و بیشتر قابلیت‌های دستهٔ ۴ (فقط یک تست برای آرشیو، `clearHistory` و فیلتر جستجو هست؛ خوانندگان پیام، نشست‌ها و خروجی داده در UI تست ندارند).

### ۳.۴ دیپلوی روی اروان

مسیر پیشنهادی: سرور ابری + داکر کامپوز. راهنمای کامل در [`arvan-deploy.md`](arvan-deploy.md).

```bash
# روی سرور
git clone <repo> /opt/hssngram && cd /opt/hssngram
cp apps/server/.env.example apps/server/.env
nano apps/server/.env      # PUBLIC_URL, JWT_SECRET, POSTGRES_PASSWORD, TURN_SECRET, DOMAIN

docker compose up -d --build
docker compose ps
docker compose logs -f app

# ساخت ادمین (فقط بار اول)
docker compose exec app node apps/server/dist/cli/seed.js
```

**سرویس‌های کامپوز:** `app` (پورت داخلی 8080)، `db` (postgres:16-alpine)، `caddy` (TLS خودکار + WebSocket)، `turn` (coturn با `network_mode: host`).

- `Caddy` گواهی Let's Encrypt را برای `DOMAIN` خودکار می‌گیرد؛ پورت‌های ۸۰ و ۴۴۳ باید باز باشند.
- مایگریشن‌ها با `MIGRATE_ON_START=true` روی استارت اجرا می‌شوند؛ اجرای دستی لازم نیست.
- فایروال: `22/tcp`، `80/tcp`، `443/tcp`، `3478/tcp`، `3478/udp`، `49160:49200/udp` (دو مورد آخر برای TURN).
- بکاپ روزانه: `pg_dump` از سرویس `db` (نمونهٔ cron در `arvan-deploy.md`).
- به‌روزرسانی: `git pull && docker compose up -d --build`.
- دیپلوی خودکار: `.github/workflows/deploy.yml` با سکرت‌های `ARVAN_HOST`، `ARVAN_USER`، `ARVAN_SSH_KEY`، `ARVAN_APP_DIR`.

## ۶. ریسک‌ها و بدهی فنی

### ریسک بالا

1. **تماس واقعی هرگز تست نشده است.** تست موجود فقط چرخهٔ سیگنالینگ و پاسخ ICE را می‌سنجد؛ هیچ تستی مدیای واقعی، `getUserMedia`، رفتار TURN پشت NAT سخت یا کیفیت صدا را پوشش نمی‌دهد. تا تست دستی روی دو دستگاه در دو شبکهٔ مختلف (مثلاً Wi-Fi + دادهٔ موبایل)، «تماس کار می‌کند» یک فرض است نه یافته.
2. **SFU ندارد.** تماس‌ها mesh کامل P2P هستند: هر شرکت‌کننده به همهٔ بقیه اتصال مستقیم دارد. با سقف ۴ نفر، پهنای باند و CPU کلاینت مکعبی رشد می‌کند و روی موبایل ضعیف یا آپلود کم، تماس ۳–۴ نفره می‌شکند. افزایش سقف بدون SFU ممکن نیست.
3. **جستجو ایندکس GIN را دور می‌زند.** در `searchMessages` شرط به‌صورت `to_tsvector(...) @@ plainto_tsquery(...) OR m.body ilike $3` نوشته شده و همین `OR` باعث می‌شود پستگرس نتواند از `messages_search_idx` استفاده کند و به seq scan برود. با دادهٔ کم تفاوت دیده نمی‌شود، ولی روی جدول بزرگ کندی خطی می‌شود و ایندکس عملاً هزینهٔ نوشتن بدون فایده است.
4. **آرشیو فعلی داده را «گم» می‌کند.** چت آرشیوشده از `GET /chats` حذف می‌شود و UI تب آرشیو ندارد؛ کاربر راهی برای دیدن یا خارج‌کردن آن ندارد. این یک باگ تجربهٔ کاربری است، نه فقط قابلیت ناقص.

### ریسک متوسط

5. **محتوا روی سرور خواناست.** هیچ Secret Chat یا E2E وجود ندارد؛ ادعای «خصوصی» فقط به معنی «خودمیزبان» است. اگر این انتظار در محصول جا بیفتد، انتظار کاربر را نقض می‌کند.
6. **پوشش تست دستهٔ ۴ نازک است.** فقط یک تست برای آرشیو، `clearHistory` و فیلتر جستجو نوشته شده؛ مسیرهای حساس «چه کسی خوانده است؟»، پایان نشست و خروجی داده تست خودکار ندارند و می‌توانند با تغییر ``/auth`` یا ``hydrate`` بی‌صدا بشکنند.
7. **پیش‌نویس فقط محلی است.** `localStorage` یعنی پیش‌نویس بین دستگاه‌ها و پس از پاک‌کردن کش از دست می‌رود؛ انتظار «همگام» را برنمی‌آورد.
8. **محدودیت نرخ در حافظهٔ پروسه است.** با ری‌استارت صفر می‌شود و با چند instance (یا چند replicas پشت Caddy) بین پروسه‌ها مشترک نیست. برای یک خانواده کافی است؛ برای رشد نه.
9. **بدون مانیتورینگ و لاگ ساختاریافته.** فقط `LOG_LEVEL` و لاگ متنی؛ خطای تولید بدون هشدار خودکار کشف می‌شود. فقط یک چک HTTP در پنل آروان توصیه شده است.

### بدهی کوچک و مستندسازی

10. **README قدیمی است:** «۲۴ تست» می‌گوید، واقعیت ۳۳ است؛ فهرست قابلیت‌ها هم دسته‌های ۱–۳ و آرشیو را کامل منعکس نمی‌کند.
11. **بدون git tag:** نسخه‌ها فقط در `package.json` هستند و هیچ‌کدام tag نشده‌اند؛ بازگشت به نسخهٔ قبل مبهم است.
12. **نسخه bump نشده:** تغییرات دستهٔ ۴ روی `0.2.0` مانده‌اند؛ باید `0.3.0` یا `0.2.1` شود.
13. **قالب‌بندی working tree:** خط ادغام‌شده در `chats.ts` و newlineهای اضافی پیش از commit تمیز شود.
14. **تست UI وجود ندارد:** هیچ E2E مرورگری (Playwright/Cypress) نیست؛ رگرسیون‌های رابط فقط دستی پیدا می‌شوند.
15. **تک‌کانتینر و Socket.IO:** مقیاس افقی بدون sticky session یا آداپتور Redis کار نمی‌کند؛ فعلاً یک instance طراحی شده است.

## ۷. قدم بعدی

**پیشنهاد اصلی: دستهٔ ۴ را ببندید و منتشر کنید — نه اینکه قابلیت جدید شروع شود.**

1. **تمیزکاری و بستن دستهٔ ۴ (نیم روز):** تب/فیلتر آرشیو در `Sidebar` + مسیر بازگشت، اتصال `clearHistory` به `DELETE /chats/:id/messages` و دکمهٔ «پاک‌کردن تاریخچه»، کنترل فیلتر `kind` در دیالوگ جستجو، fallback کپی متن، رفع نقص قالب‌بندی `chats.ts`.
2. **تکمیل تست دستهٔ ۴ (نیم روز):** تست آرشیو/`clearHistory`/فیلتر `kind` اکنون هست؛ باقی‌مانده: نشست‌ها، خوانندگان پیام و `/export`، سپس `npm run typecheck`.
3. **بازبینی جستجو (یک روز):** ستون `search_vector tsvector` تولیدشده + ایندکس GIN روی آن، و جایگزینی `OR ilike` با `UNION` یا `pg_trgm`؛ سپس `EXPLAIN ANALYZE` قبل/بعد روی دادهٔ حجیم. این تنها بدهی فنی است که با رشد داده بدتر می‌شود.
4. **تست واقعی تماس (نیم روز، نیازمند دستگاه):** تماس ۱:۱ روی دو شبکه و تماس ۳ نفره با TURN؛ ثبت نتیجه در همین سند. تا این انجام نشود، بخش تماس را «آزمایش‌نشده» بدانید.
5. **انتشار:** bump به `0.3.0`، `git tag v0.3.0`، به‌روزرسانی عدد تست در README، سپس `docker compose up -d --build` روی اروان و `curl -f https://hssngram.hssn.my.id/api/health`.

**قدم بعدی محصول (پس از انتشار):** از خوشهٔ «اعتماد و کنترل» شروع کنید — `noforwards`، هشدار ورود جدید، ban زمان‌دار و لاگ Recent Actions؛ این‌ها کم‌هزینه‌اند و مستقیماً حس امنیت را می‌سازند. SFU و Secret Chat را به‌عنوان پروژهٔ جدا با برآورد مستقل ببینید، نه بخشی از یک دستهٔ معمولی.
